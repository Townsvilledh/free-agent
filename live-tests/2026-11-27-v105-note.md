# Lille 1.0.5 — kill the "why paused" confabulation

versionCode 28 / versionName "1.0.5". Born of the 2026-11-27
~09:12 on-device failure on 1.0.4: "kill all task" was answered
by the BRAIN (which claimed a stop it never performed), the
re-adopted X card paired "already under way" with "paused
here", and "why paused" drew a long confabulation — tools
"aren't available in this environment", SHE stopped the task,
"instructions you can run locally", "a future environment" —
every clause false. Corrected sequence (Ethuram, ~09:16): the
X card was HIS deliberate re-tap after the kill, not a kill
failure; kill coverage of packaged tasks was unproven, so this
build verifies it in code and pins it in tests rather than
assuming either way. Built in
`~/workspace/.worktrees/lille-104` under his standing go-ahead
for Lille builds in that worktree.

## 1. Kill-all is a command, not a conversation

There was NO deterministic kill handler in 1.0.4 — the intake
fell through to JobDetect/the brain, which is how a claim of
stopping replaced the deed. New `TaskControl` (pure):

- Whole-message kill shapes ("kill all task(s)", "stop/cancel
  all …", "kill everything", "kill all work") are intercepted
  in the chat intake BEFORE JobDetect and the brain — the
  same conservative exact-shape discipline as the status
  probes; lookalikes ("kill the lights", "please kill all
  tasks now") are not commands.
- The deed: every non-terminal record in the store — general
  AND packaged lanes, one store, one lane-blind predicate —
  is cancelled through the normal worker path and stamped on
  the record: `killedByUser`, the verbatim command, and a
  "killed" entry in the event log. The reply is composed from
  what was actually stopped ("All active tasks have been
  stopped." / "Stopped — X." / "No work was running — nothing
  to stop.").
- Killed is terminal: CANCELLED has no outgoing transitions,
  is excluded from resumable/waiting selectors, and the
  watchdog/budget machinery only ever touches waiting states
  — a killed task cannot auto-resume. Two kill-race guards in
  TaskRunner (entry + the RUNNING door) keep a mid-flight run
  from writing onto a just-killed record.
- Every surface renders a killed task identically:
  "Stopped — you stopped this." (status card headline +
  detail, probe status line), "· stopped" (chat-list mark,
  record form), and the reason probe names his command.

## 2. "Why paused" answers from the record — never the brain

`StatusProbe` gains reason probes (whole-message exact:
"why", "why paused", "why did you stop", "why is it
stopped/paused", "why isn't it running/working", "why is it
stuck/waiting", "what happened"). The answer is composed ONLY
from the task record, one or two plain lines, in place:

- killed → his own command named back ("your message was
  'kill all task'");
- waiting on a budget rest → not paused at all: resting, and
  it continues on its own (retry time stated);
- parked at a wall → the exact step waiting on him;
- paused → approval wait (record field) → browser takeover
  (his hand) → the recorded note, vetted through
  NarrationGuard → or the honest "the record doesn't say
  why" — a cause is never invented;
- running/queued/waiting otherwise → "isn't paused", with
  the truth of its state;
- finished/failed/exported → their recorded outcomes.
- Job-shaped lookalikes ("explain why paused trading is
  risky", "why is the sky blue") are NOT intercepted — the
  existing lookalike discipline, pinned.

Restart honesty (the correction's added scope): re-adopting
a live paused/parked run from its chat action now stamps the
pickup on the record — `restartedAt`, `resumedAtStep` (the
step count the earlier run left), `restartCount`, a
"restarted" event — and the reason answer confesses it:
"You restarted it — it picked up at step 35." Verified in
code, not assumed: a post-kill tap can never resurrect the
killed record — `XAccountTask.create` always mints a FRESH
record (new id), CANCELLED is terminal, and the live search
that feeds re-adoption excludes terminal records; a fresh
record carries no kill fields and no inherited steps.

## 3. Renderer coherence

The "already under way — paused here" pairing came from the
re-adopt acknowledgement composing a live-branch prefix with
a state line. `StatusProbe.liveAckFor` now grants "already
under way" ONLY to live states (queued/running/waiting);
every other state gets its own status line — and the X
lane's three live-branch acks all route through it.
`TaskTransparency.statusText` headlines a killed task
"Stopped" (detail "You stopped this."), and a label-
exclusivity sweep pins every state × surface: no card, ack,
probe line or list mark ever pairs a working label with a
paused/stopped one.

## 4. Chat capability grounding + the guard rule

- `CapabilitySheet` (pure): a deterministic fact block built
  from the build's feature set + LIVE connection state —
  browser in any job: yes; Gmail connected, or "connect it
  in Settings — never say email tools are unavailable";
  calendar: yes; wallet families actually present; code/
  video: the computer lane hand-off ("never say those tools
  do not exist"); X lane state (verified handle / creation
  in progress / not created); the LAN extra brain when
  configured; a closing rule against capability denial and
  local-instruction offers. It rides every chat system
  prompt (all three former SYSTEM_PROMPT call sites), in
  plain terms the model can quote but not contradict.
- `ChatOutputGuard` gains the capability-denial verdict:
  negation bound to "available in this environment",
  tools/capabilities/features declared unavailable, "you
  can run it locally" instruction offers, "wait for a
  future environment" — over prose only, after the existing
  placeholder/self-dialogue checks. On rejection the chat
  regenerates ONCE on the next route with the sheet
  re-asserted in the prompt; if it recurs, the reply is
  replaced with one grounded line from the sheet
  (`CapabilitySheet.GROUNDED_LINE`). The screenshot's
  paragraph is a pinned negative fixture, clause by clause;
  legitimate hand-offs ("that part needs the computer lane —
  I've sent it there") and partial states ("Gmail isn't
  connected yet — one step in Settings connects it") are
  pinned positive fixtures that pass untouched.

## Honest limits

- No device in this environment: the kill, the reason probe
  and the grounded chat are JVM-proven and code-reviewed;
  their first on-device exercise is Ethuram's install walk,
  as with 1.0.2–1.0.4.
- The intake order (wallet → kill → reason probe → status
  probe → approvals → undo → recipes → JobDetect) is
  Android-coupled glue; every branch it can take is a pure
  function pinned by the suites above, and the zero-model-
  call property of the kill/probe paths is structural (they
  return before any brain call site), not a runtime log
  assertion.
- Kill shapes are whole-message exact by design: "please
  kill all tasks now" still reaches the brain. The bare
  forms from the screenshot are covered; widening is a
  deliberate non-goal (the lookalike discipline protects
  real jobs).
