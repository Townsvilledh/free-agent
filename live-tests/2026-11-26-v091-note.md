# v0.9.1 — device-lane rate-limit stall: diagnosis + fix

## The live stall (evidence, 2026-11-26, Ethuram's phone)

The first live device-lane run — the in-app task "Lille: create
my X account" (lane=device) — sat at **steps=3, state=
waiting_route** across repeated checks. Ethuram's screenshots:
the task screen showing "Free route rate-limited — task is
waiting, not failed", and her browser session parked on the
Maildrop homepage (where step 3 had taken her). His shared
graded report confirmed: no acceptance criteria evidenced yet,
steps done: 3.

## Diagnosis (verified in code)

`android/app/src/main/java/org/freeagent/app/TaskRunner.kt`
fired model calls back-to-back in its step loop with **no
pacing between successful calls** — browser actions paced
themselves inside BrowserSession; brain calls did not. The
keyless anonymous tier tolerates roughly one call per ~45 s
per IP (the host loop only works with `--pace 50`). She burned
her first calls fast, tripped 402/429, and the recovery waited
only Retry-After-or-45 s before the worker retried — too short
once the tier is tripped — so each wake-up's first call could
re-trip instantly: 429 → wait → 429 forever, steps frozen.
WorkManager's exponential backoff (60 s base) did not save her,
because the re-trip happened on the first call of every wake-up
if the route had not cooled.

## The fix (v0.9.1)

- `BrainPacing.kt` — a small pure component (BrowserPerception
  style) holding the arithmetic:
  - `remainingIntervalMs`: 50 s minimum interval between brain
    calls, from a persisted `lastBrainCallAt`.
  - `cooldownMs`: 60 s × 2^streak on 402/429; a larger
    Retry-After wins; capped at 15 min.
  - `nextCounter`: streak +1 on 402/429, reset to 0 on HTTP 200.
  - Plain-language notes that state the wait ("Free route
    rate-limited — next try in ~4 min (task is waiting, not
    failed)").
- `TaskRunner.kt` — the loop consults the pacing gate before
  every brain call (an early call becomes a waiting_route
  pacing wait for the remainder), stamps `lastBrainCallAt`
  into the record before each call, applies the escalating
  cooldown + streak increment on 402/429, and resets the
  streak on the first 200.
- Tests: `BrainPacingTest` (11 tests) — interval enforcement,
  escalation sequence, 15-min cap, reset-on-200, Retry-After
  winning when larger (and losing when smaller), note wording,
  and old-record compatibility.
- **Compatibility (critical):** the two new record fields are
  additive with defaults (0 = never called / no streak). The
  task store schema is unchanged (schemaless JSON records), so
  Ethuram's existing task — checkpoint at steps=3, WebView
  session in the app's data — resumes under the new code after
  an in-place update. `oldShapeRecordDefaultsCleanly` reads a
  0.9.0-shaped record through the new defaults to pin this.
