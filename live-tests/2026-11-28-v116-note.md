## Class 1 — finish-vs-steps consistency (core + device mirror)

`finish_consistency` (free_agent/loop.py) runs at finish
acceptance, after the existing evidence gates, and judges
the summary against ALL content the run produced — tool
observations AND the model's own step texts/working —
under four structural checks:

- **Weekday**: a date assertion naming a weekday the
  calendar disagrees with contradicts itself on its face
  (deterministic calendar math, no content needed).
- **Step dates**: dates the run itself produced (execution
  observations + her step texts) are its settled values; a
  summary asserting dates of which NONE is among them
  contradicts its own steps (the schedule-b shape).
- **Anchored numbers**: a numeric segment (a line/sentence
  carrying 2–12 numbers) asserts a result (its last number)
  for a calculation anchored on its first number. Two
  segments — one in the summary, one in the summary or the
  produced content — sharing an anchor, overlapping by at
  least half their number sets (Jaccard ≥ 0.5, so a
  summary sentence listing several answers is not mistaken
  for one calculation), with one side's result figuring in
  the other's numbers, yet asserting different results,
  contradict each other (the numbers-a shape — headline
  vs her own closing working).
- **Research items**: a report listing external items
  (markdown headings / bold-led list entries) is a content
  claim — every listed item must trace to a fetched source
  present in the step record (its normalised title, a
  title bigram, or, for a short title, all its words in
  the corpus). This EXTENDS the 1.0.15 evidence-demand
  machinery from file content to report items over the
  same corpus the evidence gates already read; it is not
  a parallel gate. Judged when the finish lists ≥2 items,
  or ≥1 under a fetch demand.

Verdict discipline: a contradiction bounces the finish
ONCE with the contradiction named and the step evidence
quoted; the bounce ledger (`consistency_bounces`) rides
the checkpoint. A second contradictory finish is refused
and the task parks honestly — status stopped, a
`finish-refused` step and the contradiction on the record
— never a landed self-contradicted answer. The
deterministic close (pending finish) judges consistency
with `count_offence=False`: it refuses to close on a
contradiction but never spends or triggers the verdict
(the model never saw a steer). False-positive budget: a
bounce continues the loop and fails nothing outright;
no-demand/pure-drafting finishes are judged only on facts
the run itself produced, so drafting with no produced
facts stays free of the tracing requirement.

Device mirror: `FinishChecks.consistencyContradiction`
(the same four checks over the record's observations +
assistant texts) gates TaskRunner's finish branch — bounce
once via the `consistencyBounces` record field, park
(PAUSED, `finish_refused` event, contradiction on the
record) on the second — and `applyPendingFinish` refuses
to close on a contradiction.

## Class 2 — malformed-call recovery (core + device mirror)

The old text path stopped the run when a malformed call's
single in-step repair also failed — two strikes inside one
step, whatever the task had left. Now the loop keeps a
repair ledger per CALL SHAPE (the tool the attempt named +
the parse failure's category; `_malformed_shape`):

- A shape's first malformation earns a repair re-ask
  showing the SPECIFIC format error (what was malformed,
  what the expected shape is) and does NOT count toward
  any stop. The re-ask is a format correction only — it
  never widens Sentinel permissions and never changes the
  task.
- A repair reply that malforms in a DIFFERENT shape earns
  that shape its own re-ask (bounded re-asks per step); a
  repair reply that is plain text falls through to the
  ordinary no-call handling.
- Only a malformed call AFTER its shape's repair re-ask
  counts as a strike (`malformed_strikes`); two strikes
  stop the run honestly, and the record shows the repairs
  were attempted (every malformed step names its shape and
  whether it was a repair re-ask or a strike). Native
  calls with unparseable arguments ride the same ledger:
  the first earns the repair re-ask as its observation,
  a repeat counts a strike.

The ledger (`malformed_repairs`, `malformed_strikes`)
rides the checkpoint, so a resumed run keeps the verdicts
its earlier segment earned. Device mirror: `MalformedRepair`
(shape + reason + steer texts, pure) wired into
TaskRunner's no-call branch — a JSON-shaped attempt that
failed to parse earns its shape's repair steer (spending
no failure budget); post-repair repeats strike, and
MAX_STRIKES parks the run PAUSED with a `malformed_stop`
event naming the shape and the repairs attempted.

## Limits, honestly

- The consistency checks judge only what the run produced:
  a run that computes nothing and asserts a wrong date in
  perfect agreement with its own (wrong) step text is not
  caught — the mechanism enforces agreement with her own
  working, not the working's correctness. (Round 3's actual
  schedule-b trace asserted the wrong date consistently in
  text and finish; what this build guarantees is that a
  finish can no longer overrule a DIFFERENT value her
  steps settled, and that a weekday-mismatched date can
  never land.)
- Anchored-number segments are a heuristic over numeric
  prose: the Jaccard + membership guards keep multi-answer
  summaries safe (pinned), but an adversarial summary can
  still false-bounce — by design the cost is one bounce,
  and parking requires the SAME contradiction asserted
  again after the steer named it.
- Item tracing is title-level: an item whose title traces
  but whose stated details (deadline, prizes) were invented
  is caught only where those details are numbers/dates the
  other checks judge.
- The device runner's TaskRunner wiring is CI-compiled and
  JVM-pinned at the pure halves, as in every round; the
  on-device exercise remains Ethuram's install walk.
