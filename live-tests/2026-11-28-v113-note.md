## The diagnosis (what actually failed on 1.0.12)

The screenshot message — "I need you to edit on github so all
user of lille refferal link comes in a shortened for not the
way it was in my ss" — was walked through the shipped
classifier by hand:

- The **strong JobDetect rule** needs a world-action verb from
  its list bound to the target ("edit" was in no verb list; the
  target-anchored rules that exist cover posting and
  connecting, not editing).
- The **ambiguous band** needs a work verb at the message's
  HEAD — where the direct-instruction wrapper "I need you to"
  sat instead.
- So **no task record was ever created**. The message fell to
  the brain, which answered a task as a conversation — and no
  guard verdict existed for an intake questionnaire asking for
  HER facts (the identity-ask verdict covers only
  handle/email/password/phone), so the ask-list shipped.

The second screenshot is the same disease on another surface:
"bring up mu fluid wallet" and "just call the ui" fell to the
brain, which NARRATED actions ("I'm launching the Fluid wallet
UI now. You should see the wallet screen appear on your phone
momentarily.") that nothing executed. His verdict: "This is
just hallucinations."

## His ruling, and how the fix is shaped by it

"I don't want hardcodes I want a smart and proficient that can
distinguish task and handle them proficiently." So this build
adds **no new sentence grammars** — an earlier draft of this
fix did exactly that (verb lists, wrapper strippers, a UI
grammar) and was reverted before shipping. What ships instead:

**INTELLIGENCE-LED (the new discrimination):**
- **The IntentContract.** Every chat system prompt now ends
  with a strict output contract: the reply must open with one
  verdict line — `INTENT: TASK`, `INTENT: COMMAND
  wallet|fluid|settings|chats`, or `INTENT: CHAT`. TASK = the
  message asks her to DO work needing tools, the live world,
  or time, in any domain. COMMAND = bring up one of her
  screens. CHAT = everything else, including content she can
  fully produce by replying (drafts, translations,
  explanations). The contract also states: never narrate an
  action instead of issuing its verdict; never ask for
  information; the only asks are physically his.
- **Record-first execution.** One funnel (`settleBrainReply`)
  receives EVERY route's finished reply. The verdict is
  executed BEFORE any reply text is composed: TASK creates
  the task record from the user's own message and starts its
  lane, and the delivered reply is the record's start
  acknowledgement — the model's text is discarded entire, so
  narration physically cannot precede the action. COMMAND
  performs the navigation, then delivers the performed fact's
  line. An unknown screen gets one honest line. CHAT strips
  the verdict line and the body is guard-screened and
  delivered as before. A reply with no verdict is CHAT whole
  (the pre-1.0.13 behaviour, still screened).
- **The stream gate.** While a reply streams, the live bubble
  shows nothing of a forming verdict and NEVER shows a
  TASK/COMMAND verdict's text — narration cannot precede the
  action on screen either. A CHAT verdict streams its body
  with the verdict line stripped.

**DETERMINISTIC (unchanged or frame/state machinery):**
- The existing grammars are untouched: kill/resume, browser
  open/close, log-out/switch, the probe family, and
  JobDetect's first stage (it still catches the clear jobs
  deterministically, zero model calls; its file carries a doc
  note recording the second stage). Conversation lookalikes
  are pinned against the SHIPPED JobDetect: questions about
  work, instruction frames wrapped around non-jobs ("I need
  you to tell me a joke"), and content requests ("write a
  tweet…") all stay chat through it.
- **UiScreens** — an execution table only (contract token →
  activity → reply line). There is no UI sentence parser to
  grow.
- **The guard's new verdicts** (frame/state shapes, on the
  chat AND report paths): **information-ask** (a request
  frame × an information object — her records: repo, branch,
  files, API key, credentials; or any fetchable fact: links
  bound to transfer frames, so asking HER "what's the Discord
  link?" stays clean — she answers from knowledge; being
  asked to SEND one is blocked), **intake-ask** (≥3 DISTINCT
  input-request frame types in one reply — the questionnaire
  shape; the distinct-type bar is the precision: the
  screenshot reply carried please-share / let me know / tell
  me), **action-claim** (first-person claim verb × action
  referent — progressive, perfect, imminent, and
  "you should see … appear" shapes; the report path narrows
  to UI referents so step-backed lane summaries pass).
  Fallbacks: OWN_FACTS_LINE (asserts her repo and the
  boundary, invites the job) and ACTION_LINE (the honest
  negative + the screens she can bring up), both themselves
  clean under every verdict, pinned.
- **Own-product target.** A repo job about her own product
  stamps `Townsvilledh/free-agent` on the record at creation,
  states it in the job's first status, and posts it into the
  run as a fact ("never ask the user for the repository, its
  files, or any credential"). Her repo also rides the
  CapabilitySheet, with the ask boundary.
- **Proactivity.** Routed-partial and needs-runner chat
  reports now end with her next own move ("Next from me: …"),
  verified for the repo-lane path in the matrix below.

**THE BOUNDARY (his sharpening, 2026-11-28 ~09:07):** the
ONLY things she may ask for are what is physically HIS — a
login/access step only he can perform (signing in to GitHub
in the parked browser panel), a code he types there, an
approval. Information is never asked: not links, not file
locations, not "which repo/file" — a fact she doesn't hold,
she fetches herself or derives from her state. Pinned both
sides: "share the repository URL / Discord link / which file"
variants = blocked; "sign in to GitHub in the browser panel
so I can push" = clean.

**OUT OF SCOPE, kept out:** the referral-link shortening
itself — no Referral/invite code was touched. That job is
Lille's own task to carry through this engine.

## Honest limits

- The classification is only as good as the serving model.
  On the keyless Horde route it is 10/13 with the failure
  modes above; on Pollinations (GPT-OSS 20B) and his own-key
  Groq (120B) it should be stronger — unproven until those
  legs run (Pollinations was capped; Groq is owed from the
  main context / on-device).
- A model that ignores the contract entirely (case 5) falls
  back to the pre-1.0.13 behaviour: the reply is shown,
  guard-screened. The guard catches asks and action claims in
  it, but cannot start a task the model never verdicted.
- While a weak model rambles BEFORE its verdict line, the
  stream gate may briefly show preamble text; the settled
  reply is always the executed one. TASK/COMMAND verdict text
  itself is never displayed.
- On-device proof is his install walk: wrapped instructions
  starting records, UI demands opening screens, and the
  referral-shortening job — hers to carry — running through
  this engine end to end.
