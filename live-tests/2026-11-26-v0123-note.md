## Item 1: chat bubbles render markdown

Reported by Ethuram from his phone, with the Agentware
screenshots: Lille's replies showed the model's raw markdown
as literal characters — `**`, `##`, `###`, backticks and `-`
bullets as text — nothing like the clean rendering he gets
from Muse.

**Fix:** a new pure component, `ChatMarkdown` (house style —
no Android, no I/O, JVM-pinned; no library added, the APK
grew by only ~16 KB). It renders the subset the models
actually emit:

- `**bold**`, `*italic*`, `***both***` (nesting works)
- `#`–`######` headings — marker gone, larger + bold, level
  kept for the size step
- `-` / `*` / `+` bullets shown with a `•` glyph; `1.`
  numbered lists keep their numbers
- `` `inline code` `` and fenced code blocks — monospace on
  a tinted background; code contents are literal, markers
  inside code are never re-parsed
- paragraphs and line breaks preserved; anything outside
  the subset (an unmatched `**`, a `#` with no space) stays
  literal instead of being swallowed

`MainActivity.styledText` converts the renderer's spans to
Android styles at every bubble text site — the `appendLine`
factory, the queue-badge re-renders, the dequeue restore,
and the live reply bubble (`replaceCurrentReply`) — so
stored replays, user sends, Lille's replies, queued bubbles
and status text all render the same way. Composition with
v0.12.2: the rendered text is the full readable text with
markers removed, so long-press selection copies clean text;
a message with no markdown renders byte-identical, and the
Send→Stop morph, the queue and scrolling are untouched.

**Pinned by test:** `ChatMarkdownTest` (17 tests) — each
construct in → expected text + span structure out, raw
markers absent for the covered subset, code literalness,
and the Agentware-shaped reply (headings, bold lead-ins,
bullets, numbered list) rendering with no `**`/`##`/backtick
surviving.

## Item 2: the chat honesty line

The same screenshots carried the worse defect: on the
community fallback route Lille answered the hackathon brief
by narrating a fully completed submission — repo created,
Trap Pack fetched, demo recorded, form submitted — none of
which happened or could have (the event had not started,
and chat has no tools). The structural fix (chat jobs
becoming verified tasks) is a separate release; this is the
chat-side guard, added to both system prompts in the app's
own words:

- Android `MainActivity` SYSTEM_PROMPT: "In chat you cannot
  perform actions: nothing you say here does anything by
  itself. Never claim to have done, created, fetched,
  submitted or completed anything you did not actually do
  through a tool in a task. When the user gives you a job in
  chat, say you are starting it and what happens next, in
  the present tense — never narrate a finished result."
- Core `free_agent/agent.py`: the same rule as
  `CHAT_HONESTY_RULE`, beside `GROUNDING_RULE`, included in
  every core system content.

**Pinned by test:** `ChatHonestyPromptTest` (3 tests,
source-pin in the ChatBubbleSelectionTest style — the
prompt is a string constant no JVM test can execute) and
Python `TestChatHonestyRule` (2 tests) on `_system_content`.

## Honest limits

- Rendering is verified by the pinned span tests + CI; its
  first on-device exercise is Ethuram's next chat (the
  standing no-device-on-this-VM caveat).
- The honesty line is a prompt guard, not a proof: a weak
  community model can still misbehave. The structural fix —
  a job given in chat becoming a task whose finish is
  verified from state — remains the queued release it
  already was.
