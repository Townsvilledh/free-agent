## What shipped

Born of Ethuram's 2026-11-27 screenshots of 1.0.5 (10:09, 10:20,
10:23) plus his "No hardcoding" constraint (10:22).

1. **Composer never locks.** The send button's face is a pure
   state machine (`ComposerAction`): text+idle → Send; text+busy →
   Send (the message appends at once, badged "queued", processed
   in order by the existing ChatQueue — badge lifecycle pinned);
   empty+busy → Stop; empty+idle → Send. A TextWatcher + the
   attachment hooks refresh the face as content changes. Stop on
   the empty state works exactly as before. Structural note:
   every deterministic command (wallet, kill, resume, probes,
   approvals, undo, recipes, JobDetect, steers) is intercepted in
   submitMessage BEFORE the ChatQueue offer — only brain-bound
   messages ever queue — so a queued deterministic command
   executes on its turn by construction, never swallowed.

2. **Targeted kill, by grammar.** `TaskControl.parseKill` is a
   structural grammar — verb (kill/stop/cancel) + referent —
   replacing ALL phrase sets (the 1.0.5 kill-all set included;
   `isKillAll` is now the grammar's All case): referents are
   "all"/"everything" (All), a demonstrative (this/that/it +
   optional work noun), or an open hint slot closed by a work
   noun (task/job/work/one) — "kill the lights" parses as
   nothing because its referent carries no work noun. A leading
   "not …" clause names what NOT to kill; the verb clause after
   it is the command ("not this task, kill this completely" —
   his exact words are a fixture, not the rule). Completeness
   adverbs (completely/entirely/fully) set the archive flag.
   Resolution (unchanged order): name → this chat's on-screen
   status card (`ChatData.lastStatusTaskId`) → most recent work;
   an unmatched name resolves to NOTHING (never a guess) and
   gets the one deterministic no-referent line. Kills stamp
   killedByUser + verbatim command (terminal under the
   watchdog, as 1.0.5); "completely" also archives the record —
   probe answers, the chats-list work mark and heartbeat
   surfacing all skip archived records.

3. **Deterministic resume (10:23 addition).** "resume" fell to
   the brain in 1.0.5 and got an intake list; now
   `TaskControl.parseResume` (same grammar family: resume/
   continue/"go on" + optional referent) intercepts it before
   the brain. The resolved record restarts in its own lane:
   waiting → `enqueueForced` (stored wait cleared, fresh
   all-routes attempt); paused (incl. the X task's budget
   pause) → `enqueue` (StepBudget.windowFor reads a spent
   window entering a run as deliberately resumed — fresh
   window); queued → answered "already under way". A record
   PARKED_AT_WALL is never enqueued: resume clears the panel
   dismissal and refreshes the browser panel, which reopens at
   the parked step (BrowserPanel already force-shows PARKED);
   the handback there is what resumes her. The resume is
   stamped (resumedByUser + event + verbatim command).

4. **Reports screened like chat.** `ChatTaskLink.reportFor`
   screens the model-written summary, note and wallStep through
   `ChatOutputGuard.verdictForReport`; a rejected field is
   withheld and the report recomposes from the record under the
   existing state contract (DONE / PARTIAL with the missing
   class named / ROUTED with receipt / PARKED naming the one
   step). The new HOMEWORK detector is a PATTERN, not the
   screenshot's sentences: "you" bound to an execution verb; a
   readiness/possession frame handing him an infinitive ("ready
   for you to…", "yours to run"); the minimised imposition
   ("you just need to…"); the choice-among-deliverables close;
   the "I can <produce> … for you" offer. The Agentware pack is
   the pinned negative fixture; three other-wording variants
   are pinned with it; the parked line ("parked at the human
   check on x.com — tap the browser panel to pass it") is the
   pinned positive and reaches reports verbatim.

5. **She never asks for her own identity (10:23 addition).**
   The guard gains the IDENTITY-ASK verdict (applies to chat
   AND reports): a request frame bound to an identity item
   (handle/username/email/password/passcode/phone), a
   chosen-for-her framing ("desired handle"), or the intake
   list (a need frame over ≥2 identity items) — structural,
   three other-wording variants pinned; identity FACTS ("your
   password lives only in your encrypted vault") pass.
   CapabilitySheet now states the fact in her context: her
   handle/mailbox/password are hers, already set up (password
   self-generated into the vault); a phone-verification demand
   is a park, never a chat question. A second identity-ask hit
   in chat lands the grounded IDENTITY_LINE instead of the
   generic plain line. The screenshot's ask-list is the pinned
   negative fixture.

6. **Probes by grammar (no-hardcoding constraint).**
   StatusProbe's two exact phrase sets are DELETED. A probe is
   now a whole message composed only of closed-class words
   (function words + ≥1 status content word); any open-class
   object breaks the parse ("update my bio", "why is the sky
   blue" still flow to the brain). Every previously pinned
   shape resolves identically (StatusProbeTest + Lille105Test
   green), and new phrasings of the same shape ("why is the
   task stopped", "is the work finished yet", "why isn't it
   running") resolve too — pinned in Lille106Test.

7. **The long-press menu is reachable — and on the live
   bubble (10:20 + 10:23 additions).** Root cause of the
   "taken out" report: bubbles were selectable TextViews
   (v0.12.2), and Android text selection swallows the
   long-press — he got selection handles + the system bar,
   never LilleMenu. (The status-bubble branch already knew:
   it set selectable=false "because selection swallows taps";
   regular bubbles never got the same treatment.) Now
   appendLine builds every bubble NON-selectable; the menu's
   Select item is the one selection door (that bubble only,
   resets on re-render); Copy lives in the menu. The menu card
   construction is factored into ONE builder
   (showMessageMenuCard) fed by MessageActions for stored and
   live bubbles alike. The LIVE bubble (both creation sites:
   renderChat's tail, replaceCurrentReply's re-creation) gets
   the same menu via attachLiveMenu: Copy/Select/Share/Reply
   act on its current text (liveReplyText, composed exactly as
   renderChat composes it); a reaction toggles against the
   flight's pendingLiveReaction and lands on the settled
   record at all three settle sites (deliverChatAnswer,
   stopReply, brainRouteFailed's terminal branch) — only when
   the chat's last message is that reply, else dropped;
   finishFlight clears any unapplied reaction (leak guard).
   Audit of other surfaces: status cards and report bubbles
   ARE stored messages, so they already carry the stored
   listener (verified in renderChat) — the live bubble was
   the only dead surface. One stated exception: the first-run
   greeting bubble is a transient non-message with no record
   to attach a reaction/quote to; it keeps no menu.
   ChatBubbleSelectionTest was rewritten to pin the new
   contract at the source (selectable=false in appendLine,
   Select item as the only setTextIsSelectable(true) on a
   bubble, attachLiveMenu at both live sites); Lille106Test
   pins the menu contents (reactions row + Reply/Copy/
   Select/Share in order) as the never-shrink guard.

## Honest limits

- JVM-proven, not yet device-proven: the widened kill/resume
  grammars, the report screen, the identity-ask verdict, the
  live-bubble menu and the selectable fix are all first
  exercised by Ethuram's install walk. The on-device facts
  they rest on (selection swallowing long-press; the panel
  force-showing PARKED) are from his screenshots + the panel
  state machine, not from a device run of this build.
- Kill/resume shapes are whole-message by design: "please
  resume the task now" still reaches the brain (verb must
  lead), exactly as with the 1.0.5 kill discipline.
- A queued live reaction on a reply that settles while a
  DIFFERENT chat is on screen still lands (the settle hook is
  per-chat, not per-render); one queued on a reply whose
  settle appends anything after it is dropped by design.
- The homework/identity detectors are pattern sets, not
  understanding: a novel framing outside the frames could
  pass, and a legit sentence binding "you" to an execution
  verb inside a report field ("the note tells you to run…")
  would be withheld — withholding is the safe direction for
  report fields, since the report recomposes from the record.
