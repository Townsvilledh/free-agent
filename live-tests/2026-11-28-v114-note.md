## Fix 1 — FINISH MUST LAND
Battery evidence: 13 of 24 tasks (code-a, research-a,
summary-a, data-a, planning-a, files-b, numbers-b,
format-a, schedule-a, …) did the work and parked in
waiting_route; the finish was a model call the dropped
route never got to make.
Mechanism: a finish is a STATE WRITE. A plain-text
completion statement after real tool work is recorded as
a PENDING FINISH (her summary, the outputs her steps
produced, the step she stated it at). When a route
failure would park the run, the loop first tries to close
deterministically; on resume the pending finish is
applied BEFORE any model call; a resumed run is also
steered ("call finish NOW — do not redo finished work").
Application re-verifies: outputs on disk, no tool work
after the statement (staleness by step count), the other
finish checks below. Core: `loop.py` (`pending_finish`,
`_try_deterministic_finish`, resume steer). Device:
`PendingFinish.kt` + TaskRunner (stamp on the no-call
branch; apply in `wait()` and at run start; FinishGate /
plan mode / unresolved wall refuse the close).

## Fix 2 — VERIFY-BY-STATE IN THE PLAIN LOOP
Battery evidence: code-b reported the min() cap applied
and fee(100000)=50 "verified"; the artifact was the
unchanged fixture (grader re-ran fee(100000)=1000.0); no
write step existed in her trace.
Mechanism: the run fingerprints the sandbox at start;
`produced` = files created or changed BY THIS RUN. A
finish claiming an output outside `produced` is rejected
back into the loop; a finish whose summary claims
verification of a code output needs an execution step
(run_python / run_tests) after that file's last change.
The system prompt states both rules. Device mirror: the
writers stamp the produced set (`write_note`,
`browser_screenshot` → `PendingFinish.addProduced`); a
finish claim with no production evidence (produced set
or a recorded write observation) is refused
(`FinishChecks.unproducedClaims`).

## Fix 3 — FINISH-DIALECT RECOVERY
Battery evidence: schedule-a's whole reply was
`finish("Workshop time conversion: …", [])` (twice);
format-a's was `finish({"name": "Adaeze", …}, [])` —
correct answers emitted as literal text, read as no
call, parked.
Mechanism: an ANCHORED finish(...) reply is recovered
as the call (positional/kwargs summary, list outputs,
dict-first-arg → JSON summary). Anchoring is the safety:
a finish(...) mentioned inside narration (code-b's fake
bash session) is never recovered. Core: `loop.py`
`_parse_finish_call`. Device: `FinishDialect.kt` wired
into `TaskRunner.parseToolCall`.

## Fix 5 — JOB-DERIVED BROWSER ALLOWLIST ON THE CORE PATH
Battery evidence: browser-a and browser-b scored zero —
browser_open was Sentinel-denied on the core path (no
job-derived allowlist existed there).
Mechanism: the core derives the Sentinel browser
allowlist from the job's own words (`tasktools.
derive_browser_domains`): explicit URLs, the service
table (incl. Wikipedia → en.wikipedia.org), and her
canonical hosts when the job concerns her own product —
the derivation the Android runner has had since 1.0.3
(`TaskTools.domainsFor`), now mirrored core-side and
merged into the run's spec context at start and resume.

## Fix 6 — TOOL OUTPUT OUTRANKS NARRATION
Battery evidence: schedule-b's own run_python printed
2026-12-11; her text answered "Friday, 14 January 2027"
— she overruled her tool.
Mechanism: dates printed by execution-tool observations
are evidence (`loop.verified_dates`). A finish asserting
dates of which NONE matches the evidence is rejected
(model path) or corrected to the single verified date
(deterministic close and the plain-text stop path, with
a grounding-correction step on the record). Device
mirror: `FinishChecks.dateContradiction` — a summary
date contradicted by the record's tool observations
bounces the finish once with the observed dates named.
