## What failed on 2026-11-27, and what changed — per failure

1. **Registry-step failure (the owner's login).** Both registry
   addresses were unreachable from his phone in a ~4-minute
   transient window; the fetch had two sources, no retry, no
   saved copy — a dead end. Now: the login gate walks
   `FluidGate.REGISTRY_SOURCES` (below), each source with up to
   2 attempts and a single 1.5 s backoff between them (pinned);
   when NO live source yields a valid registry, the gate
   resolves the typed name against the **on-device saved copy**
   (the first valid body from the highest-priority reachable
   source in the walk, kept in the identity
   prefs and riding the backup snapshot) and the login proceeds
   with the saved-copy notice on screen. Only when there is no
   valid copy anywhere does the honest "couldn't reach the
   registry" message stand.
2. **Relay-step failure (tebioba1, a referred user's FIRST
   login).** His name checked out; the WalletConnect relay step
   failed from his network, and the app pasted the SDK's raw
   error text ("Connection error: Please check your Internet
   connection") on screen — a Lille-looking failure that named
   the wrong step. Now every SDK error during a login attempt —
   the session listener's onError and the pairing request's
   onError alike — maps to `relayUnreachableMessage()`: "Your
   name checked out, but Lille couldn't reach the WalletConnect
   relay to print your pairing code. Check your connection and
   tap Connect again — nothing was connected." The SDK's raw
   text is shown nowhere on the login screen.
3. **The frozen-fallback hazard (the silent third failure).**
   The old fallback, fluidwallet.netlify.app, serves a 606-byte
   snapshot holding **2 names** (Netlify build frozen at the
   credits cap) against a live registry of 29+ — and the old
   code trusted any body it could fetch. For almost every real
   user, a fallback fetch would have answered "name not found"
   about a name that exists. Now every fetched body must pass
   `assessRegistry` (parses as a JSON object, ≥10 names) before
   it counts as evidence; resolution across sources
   (`resolveAcrossSources`) never lets an older valid copy
   settle a just-published name as not-found; and the Netlify
   URL is removed from the sources — and from the binary.

## Post-audit fix (G1) — corrected before publishing

The independent pre-delivery audit cleared this release with
one SHOULD-FIX, fixed here rather than shipped as a named
limit: if the WalletConnect stack itself failed to start, the
login screen printed `FluidLogin.initError` — the SDK's raw
throwable text — verbatim. The screen now shows
`FluidGate.walletConnectStartMessage()` ("WalletConnect
couldn't start, so Lille can't print your pairing code yet.
Check your connection and reopen Lille — nothing was
connected."); the raw text stays in `initError` for
logs/traces only. Pinned by
`FluidGateTest.walletConnectStartMessageCarriesNoRawThrowableText`.
The audit's two wording corrections are also applied above:
the retry backoff is a single 1.5 s delay (2 attempts per
source — no 3 s step ever fires), and the saved copy is the
first valid body from the highest-priority reachable source,
not "the freshest ever fetched".

## The three sources, verified live 2026-11-27 (from this machine)

- `https://fluidwallet.dpdns.org/names.json` — 200 direct, no
  redirect, 12,864 bytes, 32 names. The canonical registry.
- `https://raw.githubusercontent.com/Townsvilledh/fluid-wallet@gh-pages/names.json`
  — served as
  `https://raw.githubusercontent.com/Townsvilledh/fluid-wallet/gh-pages/names.json`:
  200 direct, no redirect, 12,864 bytes, 32 names (byte-identical
  size to canonical). GitHub's raw host — independent of the
  canonical host.
- `https://cdn.jsdelivr.net/gh/Townsvilledh/fluid-wallet@gh-pages/names.json`
  — 200 direct, no redirect, 11,658 bytes, 29 names. jsDelivr's
  CDN — a third independent host; its cache ran slightly behind
  (29 vs 32 names) at check time, which is exactly the case the
  validation floor + cross-source resolution are built for: the
  copy is valid evidence, but it cannot settle a newer name as
  not-found while another source remains.
- Excluded, with evidence: `townsvilledh.github.io/fluid-wallet/
  names.json` answers **301 → the canonical domain** — not a
  mirror; it fails at the same moment the canonical host does.
  `fluidwallet.netlify.app/names.json` answers 200 with the
  frozen 606-byte / 2-name snapshot described above.

All three sources are therefore genuinely independent hosts.
The honest defence in depth is the combination: independent
sources + validation before trust + retries + the disclosed
saved copy.

## Honest limits

- JVM/CI-proven only — no device in this environment. The proof
  still owed, named plainly: **a phone with all registry hosts
  unreachable completing a login from the saved copy** (and the
  saved-copy notice showing while it does). First on-device
  exercise is the install walk.
- The saved copy exists only after a first successful live
  fetch on that device (or a wallet name lookup, which also
  refreshes it): a brand-new install with all sources down on
  its very first login still gets the honest unreachable
  message — there is no copy to fall back to yet.
- The transient-window diagnosis for the owner's failure is
  inferred from timing (the registry was healthy from here
  minutes later); the fix does not depend on the diagnosis —
  retries + independent sources + the saved copy cover the
  window whatever caused it.
