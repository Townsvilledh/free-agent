## Part 1 — the owner gate (Ethuram's decision, 2026-11-26)

Lille's own X account is HERS alone — created and managed
from his instance only. New pure component `OwnerGate`:
`OWNER_USERNAMES = {"ethuram"}` in one clearly-marked place
("creator/owner identities — Lille's own accounts are
managed only from these"). TasksActivity renders the
"Lille: create my X account" button ONLY when the verified
Fluid login identity (FluidIdentityStore, written by the
v0.10 gate after registry + WalletConnect verification)
normalises to an owner name — FluidGate.normaliseName, so
case/whitespace/"@" variants count. Any other username, or
no verified login → the button is GONE (View.GONE, re-applied
on every refresh and immediately on disconnect), and the task
cannot be created from the UI. Test evidence for a non-owner
login: OwnerGateTest pins other-name → hidden and no-login →
hidden (7 tests, green in CI); the shipped APK's dex contains
OwnerGate wired into TasksActivity. Workers remain ungated,
as in v0.10.

## Part 2 — "Connect my X account", for everyone

The counterpart: a packaged task on the same screen, visible
to ALL users, deliberately not owner-gated (`XConnectTask`).
New tool `browser_handoff{step}` (pure logic in
`UserHandoff`, 6 JVM tests): a PLANNED user step, honoured
only on tasks whose record carries `userHandoff = true` —
set by the packaged task at creation, never by model request
alone; wall parks still require an observed challenge. The
task opens https://x.com/i/flow/login in her WebView, hands
over, and parks (kind `user_step`, flagged `userHandoffDone`)
with the "Lille needs you" card; the USER signs in themselves
in the parked session — she never sees, types, asks for, or
stores their password (the task text forbids using a pasted
password). On handback the runner injects the handoff resume
note; she verifies with `x_session_status` and the report
grades **CONNECTED — Connected as @handle** from recorded
evidence (xHandle + userHandoffDone), or an honest
NOT CONNECTED / NEEDS YOU state. The session persists in
WebView storage like her own lane's. Posting from a connected
user account stays approval-gated (`xPostMode=user`,
`xPostApproved=false`) — unchanged. Plain copy on the button
hint and in the report: "Lille will open X and wait — you log
in yourself, in her browser, then hand back. She never sees
your password."

## Part 3 — the identity kit lives in build secrets

At the owner's direction ("the x creating account shouldn't
be tampered by user via repo or any other means"), the kit —
handle preference list, bio, DOB, mailbox ladder — was moved
OUT of the public source:

- The four values were extracted programmatically from the
  pre-refactor source and set as repo Actions secrets via
  the GitHub API (libsodium sealed-box): `LILLE_X_KIT_HANDLES`,
  `LILLE_X_KIT_BIO`, `LILLE_X_KIT_DOB`, `LILLE_X_KIT_MAILBOXES`
  — all confirmed present (created 2026-11-26T10:44–10:45Z).
  Values were never printed in any log or report.
- `android/app/build.gradle`: the build step's env feeds
  Gradle's `lilleKitField` (escapes values into Java string
  literals) → `BuildConfig.X_KIT_*`; `buildConfig` generation
  enabled. The workflow passes the four secrets to the build
  step only (same mechanism as the signing key).
- `XIdentityKit.fromBuildConfig()` parses them;
  `XAccountTask.taskText(kit)` interpolates the kit into the
  task text (hard rules unchanged; the maildrop-specific
  wording was generalised to the ladder). A build without
  the secrets (source/local/fork) is hollow: creating her
  task records it FAILED with the "Owner configuration
  missing" note and never enqueues it — no baked-in defaults
  anywhere. TasksActivity toasts the same and dedupes the
  record.
- The v0.8 spec (`specs/2026-11-25-lille-x-account.md`) was
  redacted to match, with a dated note in the file.
- **Verified in the shipped artifact:** the kit is present
  in the APK's dex (handles, DOB, and all three mailbox
  domains checked as booleans — values not printed),
  alongside OwnerGate, XConnectTask, and browser_handoff.
- **Correction made during shipping:** the first secret-set
  pass captured the third mailbox domain WITHOUT its TLD
  (a regex stopped at the first dot). Caught by the artifact
  dex check, the secret was re-set from the pre-refactor
  source in git history with a domain-aware extraction
  (updated 2026-11-26T10:55:50Z), the build re-dispatched,
  and the shipped artifact re-verified — all three domains
  present in full. That re-dispatch was fix cycle 1 of 2;
  no code fix cycles were needed (both code builds were
  green first try).
- Known remainder, stated plainly: the kit values remain in
  this repo's **git history** up to commit `71df9f1`, and in
  one dated evidence file, `live-tests/2026-11-25-v08-proof.md`
  (the v0.8 run's graded record — left untouched rather than
  rewriting evidence). Removing them from history would be a
  separate, deliberate history rewrite — the owner's call.
