## What was built

1. **Widened session proposal** (FluidGate.proposalChains /
   proposalMethods, consumed by FluidLogin.connect): the
   session now asks for `personal_sign` +
   `eth_sendTransaction` on all seven of her wallet's chains
   (eip155:1/8453/42161/137/56/43114/10). Identity
   verification is byte-for-byte the v0.10 logic — the
   connected account must still equal the typed name's
   registry address. Correction recorded in PARITY.md row 3:
   Fluid accepted eth_sendTransaction all along (Fluid build
   stamp 4d7f509193); the gate was Lille's minimal proposal.
2. **Honest degradation**: FluidLogin.grantedFor reads what
   a live session actually granted; FluidTx.txAvailable /
   txUnavailableReason decide per chain. A personal_sign-only
   session still logs in; a main-wallet send on it reports
   "approved for sign-in only" with the remedy, before
   anything is prepared. Pinned by tests.
3. **Main-wallet send flow** (FluidTx + WalletEngine
   .prepareFluidSend + MainActivity.handleFluidWalletPrompt
   + WalletActivity source checkbox): chat phrasing +
   trailing `from fluid` / `from my fluid wallet`, or the
   Wallet screen's "Send from my Fluid wallet instead"
   checkbox. Live prepare (registry resolution, live-price
   USD conversion; NO balance/fee/nonce — those are Fluid's),
   payload gate, embedded Fluid sheet opened, then
   eth_sendTransaction over the session. Fluid's own sheet
   approves; chat reports the tx hash or Fluid's error
   verbatim. Companion flow untouched and still the default;
   no caps and no autonomous path exist for main funds.
4. **Payload discipline** (FluidTx.validateCall, applied at
   prepare AND again immediately before the request): plain
   native sends and ERC-20 transfer / transferFrom / approve
   of exact shape pass; contract creation (no `to`), unknown
   selectors and malformed calldata are refused pre-send
   with a plain reason. Pinned by tests.
5. **#wc= deep link**: FluidSheetActivity takes a pairing
   URI extra and loads FluidTx.deepLink(uri)
   (encodeURIComponent-faithful, pinned); a main-frame load
   error falls back once to Fluid's plain page, and
   LoginActivity still copies the code to the clipboard —
   paste remains the fallback. Login steps text in LOGIN.md
   and the sheet's own header comment updated (both
   previously recorded "Fluid has no deep link").

## Honest limits

- No device/emulator on this VM: readiness is CI (full
  suites + build) plus the inspection walk of every touched
  flow. First live exercise is the owner's phone.
- Existing sessions were granted under the OLD proposal
  (personal_sign, eip155:1): the first main-wallet send
  needs ONE reconnect (Disconnect Fluid name → connect,
  approving the wider request) so the session actually
  carries eth_sendTransaction. Until then the degradation
  message says exactly that.
- The embedded sheet's Fluid storage is separate from
  Chrome's (standing caveat since v0.12): a wallet that
  lives in Chrome may need one create/import inside the
  sheet before Fluid can approve there.
