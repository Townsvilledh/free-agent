# Lille 1.0.9 — identity answers are LIVE reads, never stale stamps; the which-account family; no ask-backs about her own state

versionCode 32 / versionName "1.0.9". Built from the
2026-11-27 14:29–14:50 on-device evidence on 1.0.8
(his screenshots).

## What was wrong (all proven on-device, 1.0.8)

- "which x account is logged in" fell to the BRAIN —
  no probe family caught it (the login family's closed
  vocabulary has no "which"; the accounts question has
  no "logged"). The brain answered: "I don't have
  visibility into the specific X handle that's
  currently logged in. The browser on this phone is
  still showing a signed-out state (its last recorded
  page is https://x.com/home and it's marked "signed
  out"). If you've just signed in, you can verify
  which account is active by checking the profile icon
  or the URL @username in the browser yourself. Let me
  know once you've confirmed the handle, and I can
  continue any next steps you need." At that moment
  her own browser panel was open on a SIGNED-IN X home
  feed (For you timeline, compose button, notification
  badge "2", his avatar top-left) — he had signed in
  during a browser takeover earlier. Three failures in
  one paragraph: a phrasing no family caught, a STALE
  stamp quoted as current fact (in the wrong
  direction), and the reading outsourced to the user.
- "what x profile is logged in now" DID reach the
  deterministic machinery and got the verifying line —
  proof the live-check path existed but only one of
  the two phrasings reached it.
- Underneath both: the 1.0.8 identity read itself
  conflated two different pages. xHandle() returns
  null both when the browser is signed out AND when
  the handle isn't exposed on the current page (on
  mobile X it sits behind the top-left avatar) — and
  callers stamped signed OUT on null. And the
  handback verification only ran when the browser
  happened to rest on x.com at resume time; a handback
  from any other page left the verification unstamped
  forever (handbackPending never cleared).

## What shipped

1. **THE FRESHNESS RULE** (`SessionIdentity`): the
   identity stamp may be quoted as current only when
   it postdates the browser lane's last activity —
   page changes (the session's new `lastActivityAt`
   marker, stamped on page finish + collect),
   takeover starts (stamped on the record by the
   panel's WATCH action), and handbacks
   (`lastBrowserActivity` takes the max). Any
   login-state or accounts answer — probe path,
   registry path, or brain-with-sheet — whose stamp
   fails the rule (`needsLiveRead`: never read, stale,
   handback verification pending, latest read
   unreadable, re-check already owed) runs a live
   re-read FIRST. The StateSheet marks a stale
   identity as "being re-checked", never as a fact —
   in both the per-task line and the browser line.

2. **THE RE-CHECK PASS** (`TaskRunner
   .runIdentityRecheck`, `TaskWorker` identity mode):
   a read-only pass over a record — no state
   transitions, no un-parking. The chat stamps a
   request (`identityRecheckAt`/`identityRecheckChat`)
   and enqueues the pass under its own WorkManager
   name (`lille-idcheck-<id>`) so it never replaces
   the task's own pending run. It positions the
   browser when the lane may move it (a PARKED
   record's page is evidence and is read in place),
   runs the concluding read, stamps the outcome,
   syncs the registry, settles a pending handback's
   verification stamp (and lands the handback
   announcement when this read is the one that
   verified it), and completes the answer in the
   requesting chat from the record. The interim
   answer is the verifying line ("She's verifying
   that from the browser itself right now — the
   verified answer lands here from the record, not
   from messages.").

3. **THE CONCLUDING READ** (`readXIdentityHere` +
   `BrowserPerception.xIdentityShape`): every
   identity read — handback verification, lane
   start/resume, the model's session tool, the
   re-check — judges the collected page's SHAPE:
   handle in the tree → signed in as it; sign-in
   chrome and no session furniture → signed out;
   session furniture but no handle → the scripted
   reveal (the fixed `X_OPEN_ACCOUNT_MENU_JS`: tap
   the account switcher, or the profile tab whose URL
   then names the handle) and a re-read; neither →
   **Unreadable** with the reason. An unconcluded
   read stamps `identityUnreadable` (+ time) — the
   identity stamp itself is left untouched, the
   unreadable mark is the record's latest word, the
   StateSheet renders it as unknown-being-re-checked,
   the watchdog retries the read after ~5 minutes
   (`TaskWatchdog.identityRecheckIds`; terminal,
   archived and killed records excluded), and a
   handback whose read couldn't conclude announces
   exactly that, once, deterministically. The
   handback verification now also positions on
   x.com/home when the browser came back on another
   page, and a concluded lane-start read settles a
   pending handback (the panel's user-hold handback
   has no wall block to verify it). The registry is
   synced only on conclusions — an unreadable read
   never marks the platform signed out.

4. **THE WHICH-ACCOUNT FAMILY** (`StatusProbe
   .whichAccountTaskFor` / `whichAccountAnswerFor`):
   interrogative (which/what/who) + account word
   (account/profile/handle) + sign-in state, every
   token inside a closed vocabulary — joins the
   deterministic state family ahead of the login
   family and runs under the freshness rule. His two
   phrasings and reworded variants are pinned;
   lookalikes ("which account should i use for the
   signup", "what profile picture should she use")
   keep their non-interception. The answer names the
   account outright, with the read time and the same
   ownership framing as the login answer.

5. **THE ASK-BACK GUARD** (`ChatOutputGuard`,
   verdict "ask-back", chat + report paths): a reply
   that asks the user to check, verify or supply a
   fact the app itself can read — the report-back
   frame ("let me know once you've confirmed…"), the
   do-it-yourself frame ("you can verify/check/
   confirm … <own-state>"), a sentence-opening
   imperative, "tell me which/what/whether …
   <own-state>" — every shape bound to an own-state
   object word (account, handle, profile, sign-in,
   browser, page, task, status, session). The
   14:29 paragraph is the pinned negative fixture on
   both paths. Legitimate asks stay clean as pinned
   positives: the parked sign-in instructions, an
   approval ask, a preference ask, a world-fact ask
   ("let me know once you've checked the price on the
   exchange" — no own-state object). The glue's
   fallback for an ask-back hit is the record's own
   answer, with the same guard-reassert treatment as
   status-denial.

## Deliberate contract changes

- None to prior pins: `loginAnswerFor` is unchanged
  (its handback-pending branch still serves direct
  callers); `StateSheet.Facts` gains one defaulted
  field (`browserActivityAt`); `SessionIdentity
  .stamp` keeps its signature (it now also clears an
  unreadable mark and a satisfied re-check request —
  a concluded read superseding both is the point).
- The accounts-registry answer still answers
  immediately from the registry (the list is durable
  record, not live state); when its freshest backing
  read is stale it now ALSO triggers a re-check that
  syncs the registry when it lands.

## Honest limits

- No device in this environment: the first on-device
  exercise of the freshness rule, the menu reveal,
  and the re-check pass is Ethuram's install walk.
  The two page shapes are pinned against fixture
  trees (the perception layer's contract); X's live
  mobile DOM may differ in testids the fixtures
  assume (`AppTabBar_Profile_Link`,
  `SideNav_AccountSwitcher_Button`,
  `SideNav_NewTweet_Button`) — if the live page
  exposes none of them, the read lands Unreadable
  with the reason and retries, which is the designed
  failure mode, not a wrong answer.
- The re-check's handback announcement fires on a
  signed-in conclusion; a signed-out conclusion
  reached by re-check answers only a requesting chat
  (the handback block's own announcement still
  covers the in-run case).
- Ask-back shapes are sentence-local like the frames
  around them; a sufficiently indirect phrasing can
  still slip the guard — the deterministic families
  are the primary defence, the guard is the net.
