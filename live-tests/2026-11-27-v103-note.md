# v1.0.3 (versionCode 26) — THE GENERAL RUNNER GETS ITS TOOLS: browser wired in, availability declared at task start, progress-aware step budget, sleek dismissible browser panel

One release carrying the whole 2026-11-27 direction set, built on
the shipped 1.0.2 tree (main 035671e, versionCode 25). Trigger:
the Agentware task's honest graded report on-device (2026-11-27
06:23) — "the required browser, Gmail, Discord, GitHub, and video
tools are not available in this environment. Only note and
web-search tools exist" — literally true of the Android general
TaskRunner, while the packaged X lane drove 37 real browser steps
the same morning. Followed by Ethuram's restatement ("she needs
to have everything she needs to get everything done… I don't
want to keep coming back to add missing pieces") and the browser
panel verdict (expand/take-over buttons "not sleek at all", and
no close button).

1. **Browser tools in the general device runner.** A general
   on-device task whose own words call for the web now gets the
   full device browser toolset — browser_open / read / click /
   type / type_secret / upload / screenshot / wait plus
   vault_gen_secret / vault_record_account — dispatched through
   TaskRunner to the SAME executor the packaged X lane uses
   (TaskTools.executorFor, pure). The Sentinel allowlist is
   DERIVED FROM THE JOB ITSELF: the URLs and bare domains the
   job text names, plus the canonical domains of web services
   it names (discord → discord.com, github → github.com,
   lu.ma → lu.ma + luma.com, …) — recorded on the task record,
   never widened at runtime, and search results never
   auto-authorise a domain. Class-A lane rules and the
   PARKED_AT_WALL handoff are inherited unchanged; browser
   steps surface in the in-chat panel and render in the
   transparency step list with site names, exactly as X-lane
   steps do. The X tools (x_*) stay packaged-only: dispatch
   refuses them on general tasks by Sentinel, never routes
   them to the browser executor.
2. **Tool availability declared at task start.** Every general
   task is PLANNED deterministically from its text (TaskTools:
   keyword/shape detection, conservative, no model call) —
   which classes it requires (browser, mail, repo/code, video;
   notes + web search are the base kit) vs what this phone
   has. The plan is stamped on the record at creation
   (MainActivity.startChatTask) and at run start, so the job's
   FIRST chat status already declares it: what she has here,
   what needs the computer lane, and that she'll do the parts
   this phone supports and mark the rest in her report
   (TaskTransparency.declarationFor). The model hears the same
   facts as a recorded environment note before its first step.
   A finish with computer-lane classes outstanding is stamped
   partialCompletion and the graded report is labelled
   "(partial)" with the not-done classes named — never
   silently downgraded (ChatTaskLink). Mail, repo/code and
   video are NOT faked on-device; webmail-as-workaround is
   explicitly out of scope for this release. One gate narrowed
   by exactly one case: a MIXED job (code hints + browser
   required) no longer exports whole — it runs on-device with
   the declaration and the partial label; a pure code job
   still exports NEEDS_RUNNER on the original v0.4 hints,
   unchanged.
3. **Progress-aware step budget.** A task no longer parks dead
   at its step budget (the X run's 37 good steps paused at the
   40 cap, waiting for a word). StepBudget: when a window
   closes, a window that was MAKING PROGRESS (successes
   outnumber failures, no run of 3+ consecutive errors) RESTS
   ~60 s and auto-resumes on the ordinary waiting machinery
   (worker re-enqueue at nextRetryAt, watchdog app-open kick),
   up to 6 rests per task per day (a browser task can spend
   240 steps a day before the user is asked). A stalled window
   or a spent cap parks for the user's word with the original
   note. Transparency renders an armed rest as "Resting
   between work sessions — she continues on her own", and
   "paused — say continue" only when truly parked. Legacy
   records derive their window from lifetime steps (37/40 →
   37 remaining steps kept; 40/40 → fresh window).
4. **Browser panel: sleek controls + a close button.** Expand,
   Take over and Done — hand back are now small tonal icon
   buttons in the shared LilleMenu language (expand corners,
   steering wheel = take over, return arrow = hand back; the
   words live in content descriptions — BrowserPanel's pinned
   labels). The old text bars are gone. A new CLOSE control
   dismisses the panel so the chat is fully usable while the
   browser work KEEPS RUNNING — dismissal is a view fact held
   by the screen, never written to the task record; the task
   is untouched. While hidden, a slim chip ("Lille's browser
   is working — tap to view") carries the browser's presence
   and reopens the panel in one tap. If the task PARKS needing
   the user while hidden, the panel reopens on its own at the
   parked page (BrowserPanel.panelVisible / indicatorShown,
   pinned). Panel chrome is pinned against the real layout
   (BrowserPanelChromeTest).
5. **Tests.** TaskToolsTest (new): the Agentware-shaped job
   requires all four classes with mail/repo/video unavailable
   and discord.com + github.com authorised (gmail deliberately
   NOT in the allowlist); a mail-shaped job declares mail only;
   a link job requires the browser and its domains; a plain
   note job requires nothing; the intake suffix is never
   detection input; the export gate stays on the original code
   hints; plan stamping round-trips and never narrows an
   existing allowlist; the declaration text names what she has
   and what needs the computer lane, narration-clean; a general
   task drives a fake browser end-to-end through the runner's
   own dispatch rule (allowed page opens and reads, an unnamed
   domain is refused by the Sentinel gate, x_post is refused by
   dispatch, notes stay with the note executor); browser steps
   render with site names; budget pins (progressing → rest,
   errors dominating / error streak / no progress → park,
   daily cap → park, legacy window derivation, per-day rest
   counting, rest wording narration-clean, parked wording
   unchanged). BrowserPanelTest gains the dismissal truth
   table (close hides + indicator shows, tap reopens,
   park-while-hidden reopens, hidden shows neither) and the
   control-label pins. ChatTaskLinkTest gains the partial
   pin. Local JVM harness: 64 tests OK across the touched
   suites (TaskToolsTest, BrowserPanelTest,
   BrowserPanelChromeTest, ChatTaskLinkTest,
   TaskTransparencyTest). Full CI green (below): Python 230
   tests OK (3 skipped), JVM testDebugUnitTest, assembleDebug.
   PARITY.md rows 13 + 37 updated.

## Honest limits

- No device in this environment: the general runner's browser
  path is JVM-proven end-to-end against a fake driver behind
  the real Sentinel gate; the WebView driver underneath is the
  X lane's, exercised live on-device (37 real steps on 1.0.2).
  The first full LIVE run of a general browser task is
  Ethuram's install walk.
- The availability detection is keyword/shape-based and
  conservative by design: a job that needs the web without
  naming a site, a service, a link or a web action in words
  will not be detected as browser-shaped (it still has notes
  + web search, and the model can say what it needs in its
  report). False negatives are possible; false positives are
  guarded by word boundaries and action-shaped phrases.
- The budget rest reuses the waiting machinery: if the
  process is killed during a rest, the watchdog's app-open
  kick and the worker chain are the recovery, as with every
  other wait.
- Panel dismissal is per-chat and in-memory: switching chats
  or restarting the app brings the panel back with the work —
  the dismissal is a glance-away, not a setting.
