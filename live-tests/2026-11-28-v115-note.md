## Class 1 — CORE-PATH ROUTE STARVATION (the diagnosis)

What the round-2 traces actually show the router did:

- 10/24 tasks ended waiting_route. Of the 20 runs that got
  any service, the persisted checkpoint's `provider` field
  reads ai-horde in 19 — the keyless last-resort route
  carried nearly every served run. Groq (the own-key route,
  normally first in the walk) served exactly one run
  (numbers-b), which parked after a single step.
  Pollinations served none.
- Three runs parked at step 0 within ~6 seconds — no route
  ever engaged, yet the task parked instead of waiting.
- The parked tasks' `retry_at` was uniformly ≈ +300s. 300s
  is ai-horde's base cooldown — the MINIMUM over routes of
  the next unlock time. For that minimum to be horde's
  alone, Groq contributed no unlock time at all: a route
  that fails with a NON-fallback status records no cooldown
  and no unlock, so it is invisible to the wake-up math.
  Pollinations' unlock, when present, was its daily-cap
  402 carrying a Retry-After to the 00:00 UTC reset — hours
  out, never the minimum.
- Why Groq recorded nothing: the old router treated only
  {402, 429, 503} as demoting failures. Every other status
  (401/403 — a rejected key; 404 — a model the account does
  not carry, the exact failure this account's route table
  has hit before) fell through as a plain failure with NO
  cooldown recorded. The route was retried fresh at every
  step, failed identically, and the walk still ended on the
  one route that did record state — horde — whose 300s
  cooldown then became the task's park time. A mid-task
  route failure never re-walked the other routes before
  parking beyond the single pass, and nothing waited even
  seconds for a recovery that was seconds away.
- Diagnosis was partly blind by construction: router
  cooldowns/fail counts were per-process memory and the
  router's own audit trail was never persisted, so the
  records could not say which routes were tried, in what
  order, or why they were skipped. That blindness is
  itself one of the defects fixed here.

The fix (free_agent/router.py, free_agent/loop.py):

- EVERY non-fallback HTTP status now demotes its route:
  the demotion set is {402, 429, 503, 401, 403, 404},
  handled by one shared failure path for both route walks
  (complete + chat): the route records a cooldown —
  the server's Retry-After when sent, else the route's
  base cooldown doubling per consecutive failure (capped
  ×8) — and a cooling route is skipped, never retried
  blind. A single route's exhaustion can no longer consume
  a task while another route is healthy, and the wake-up
  time (the minimum unlock) now reflects every route.
- Within-route model rotation: a 404 from a route carrying
  more than one model rotates the failed model to the back
  of that route's list and retries the SAME route on the
  spare before any demotion bites — a dead model name no
  longer kills a live route.
- In-run wait-out: when a walk ends with every route
  cooling but the earliest unlock is near (≤40s), the
  router waits it out in-run (injected sleeper; bounded at
  2 waits, never re-waiting the same unlock) and re-walks,
  instead of parking a task whose route recovers in
  seconds. Longer recoveries still park — the durable
  scheduler's proactive pass already resumes parked tasks
  at their next_retry_at, and that division is deliberate:
  the router waits seconds, the scheduler waits minutes.
- The router audit tail (bounded, last 100 events) is
  folded into every loop checkpoint, so record.json now
  carries `route_events`: which routes were tried, demoted,
  rotated, waited on. Route health is record evidence from
  this build on, not process memory.

## Class 2 — ZERO-WORK FINISHES

Battery evidence: summary-b finished with ZERO tool calls,
its report a fabricated table of two wallet files'
contents (an honesty failure); browser-a's finish carried
only an error payload under a "results" key, empty summary,
outputs=[] — and was accepted.

Mechanism (core `loop._check_finish`, device mirror in
`FinishChecks` + `TaskRunner`): a finish is judged against
the task's own EVIDENCE DEMAND, derived structurally —
the plan's required tool classes, a page the task text
points at (URL/bare domain, or her own product named
alongside a quantity the task asks about), and files that
EXIST in the task sandbox AND are named by the task's
words. Against that demand the finish must carry:

- a non-empty summary (an error-payload-only finish is
  not a completion);
- at least one executed tool step when any demand exists
  (zero-work finishes on read/act tasks are rejected back
  into the loop with the demand named);
- a read step for every demanded file — a step that read
  the file by name, or an observation carrying the file's
  actual content (the verify-by-state fingerprint extended
  from claimed output files to claimed CONTENT);
- grounded values: every numeric literal the summary
  asserts (dates excluded — they have their own gate)
  must trace to a tool observation, the task text, or the
  content of a demanded file this run actually read.

A task with no evidence demand may still finish tool-free
(drafting, composing) — the gate is proportionate to the
task, not a blanket tool quota. On device, the same gates
judge both the live finish branch and the deterministic
pending-finish application, so a statement that speaks
about an unread demanded file or asserts an ungrounded
value closes nothing on either path. Rejection continues
the loop, as the existing gates do — it never writes a
failure over work that can still be done.

grounded finish lands; fabricated value rejected after
real reads; unread demanded file named in the rejection;
empty-summary finish rejected; no-demand task finishes
tool-free) + Lille115Test's pure halves.

## Class 3 — PSEUDO-TOOL-CALL TEXT

Battery evidence: browser-b's "work" was a written script
of `browser_open(...)` / `Lille: browser_read()` lines —
plain text, nothing executed; format-a derailed into
repeated failing vault/pip steps until the budget died.

Mechanism (core `loop.detect_pseudo_tool_call`, device
`FinishChecks.pseudoCallName`): a reply whose line —
after bullet/speaker-prefix stripping — OPENS with a call
shape naming a REAL tool from the live registry is a
written tool call, not prose. It is never executed as
text and never narrated as done: it is recorded as its
own step kind, it never stamps a pending finish (it
states no result), and the model is steered once,
explicitly, to emit the call through the real format. A
second pseudo-call reply stops the run honestly instead
of narrating on. Prose that merely mentions a call
mid-sentence, and code naming non-tools, are not pseudo
calls (pinned both sides).
Derailment: the loop now tracks PRODUCTIVE steps
structurally — a step is productive when it changes a
sandbox file, finishes, or produces a (tool, result) pair
the run has not seen before. Four consecutive
zero-information steps earn the record-derived
return-to-work steer (class 5); eight stop the run
honestly ("repeated steps stopped making progress") after
one attempt at a deterministic close. A loop of identical
failures can no longer burn the whole budget in silence.

Pinned: PseudoCallTests (4) — detection shapes incl.
browser-b's verbatim forms, prose/code negatives,
two-pseudo stop, pseudo-then-real recovery, derailment
steer-then-stop.

## Class 4 — FORMAT-B RUNNER/VERIFIER DIRECTORY MISMATCH

Battery evidence: two rounds, identical BLOCKED — the
spec loop executed in the task directory while the
verifier graded `repo/`; hello.txt/count.txt were written
at the task root and graded missing.

CONTRACT CHOICE: **spec tasks execute with the repository
as working directory.** Rationale: that is how spec mode
is documented and used on the host lane generally — the
spec's own notes already spoke of repo-root-relative
paths, the verifier (evaluate_criteria over repo/) already
graded that contract, and a repository task's files belong
in the repository, where the push/PR flow picks them up.
The runner was the side out of contract, so the runner
moved; the verifier is unchanged.
Implementation (free_agent/specmode.py, gittools.py):
run_spec pre-clones URL repositories host-side (falling
back to the legacy clone-first flow when the pre-clone
fails); the spec loop then runs with task_dir = the repo
root when repo/.git exists (legacy task-root otherwise),
spec.json is copied into the work dir and excluded via
repo/.git/info/exclude so it never pollutes the deliverable,
the task brief and repo notes state plainly that the
working directory IS the repo root and paths are relative
to it, and gittools.repo_dir_of resolves a task dir that
is itself a git root as its own repository (previously a
named-but-absent subdir silently won). Evidence gathering
also checks the session file at the repo root.

Pinned: SpecContractTests (3) — the Format B spec shape
end to end SHIPPED with both files inside repo/ and none
at the task root; writes at the old task-root level grade
BLOCKED honestly (the round-2 outcome, now a property of
misplaced work rather than of the contract); repo_dir_of
resolution. Existing spec/proactivity/video suites were
updated to the repo-root path contract.

## Class 5 — LOOP-CHECK DIVERSION

Battery evidence: files-b's identical-call loop detection
steered her to "browser_read the current page /
browser_open…" — Sentinel-denied on a file task — instead
of back to the files.

Mechanism (core `loop._return_to_work_note`): every loop
steer is now DERIVED FROM THE TASK RECORD at the moment
it fires — the last productive tool and its arguments,
the demanded files no step has read yet, the claimed
output not yet produced — and it names only work the job
itself calls for. The hard-coded browser steer text is
gone from the identical-call steer, the derailment steer,
and the malformed-call steer (which also lost its
"(for a browser task: …)" aside). A loop break returns
the task to its own unfinished work; it cannot introduce
a tool class the job did not call for, because the steer
is built from what the job already did and still owes.
The device runner has no equivalent generic loop steer
(its steers are format-only), so this class is core-only;
the device mirrors for classes 2 and 3 cover the shapes
that exist on device.

Pinned: LoopSteerTests (1) replaying files-b's shape —
three identical reads earn a steer naming read_file and
the still-unread files, with no browser tool named in it.

## Known bounded trade-offs (stated, not hidden)

- The own-product fetch demand (class 2) can false-positive
  on a task that DRAFTS text about her own product and
  happens to contain a numeral: its zero-tool finish is
  rejected once and the steer says why; a tool-free drafting
  finish after any single tool step, or a reworded finish,
  lands. Rejection is recoverable by design — it continues
  the loop, never fails the task.
- The derailment stop (class 3) could in principle cut a
  legitimate long poll whose observations are byte-identical
  eight steps running; the threshold counts only
  zero-information steps (any new result, file change, or
  finish resets it), and the stop first attempts the
  deterministic pending-finish close.
- The in-run route wait (class 1) is capped at 40s by
  design; minute-scale recoveries remain the durable
  scheduler's job, as before.
